## Implementation choices

On November 3, 2026, the owner approved **Evolved Getter**, the larger popup and a visible **Settings** button after reviewing the first package. The desktop toolbar popup requests 720 × 600 CSS pixels, with larger type, a shorter header, four color columns, three image columns, side-by-side font details and two-column preferences. Chrome applies its own popup and available-screen bounds; results scroll within the popup. Do not cap the intrinsic root width or window height with viewport units: Chrome auto-sizes the popup from its content, so those caps can lock it to the initial small viewport. The owner reported this in review package 2; the automatic-popup regression reproduced 278 × 346 pixels before removing the caps. A normal tab resized to 720 × 600 had missed the defect. The fixed desktop popup does not promise a 360-pixel mobile layout. Settings has a gear plus a visible label, and selecting it again returns to Colors.

Evolved Getter retains the existing product symbol's path geometry and uses a blue-to-deep-violet gradient (`#009CFF`, `#5969FA`, `#6D28D9`). It is used in the toolbar, extension manager and popup header. This is the owner's approved Getter identity change; the separate Aptelum attribution master remains byte-for-byte unchanged. Product PNGs at 16, 32, 48, 128 and 800 pixels are rendered from the SVG using resvg-js 2.6.2 with `fitTo: { mode: "width", value: size }`, transparent background and no font dependency. The renderer is an asset-preparation tool, not a runtime or build dependency.

React 18.2 and JSZip 3.10.1 are retained at exact versions. The former Webpack/Babel/plugin stack was considered for repair. For this two-entry static extension it required many packages and separate transforms; one esbuild script handles the same React JSX and background bundles with fewer moving parts. There is no framework, backend or service migration. Node 24.18.1 and the dependency lock provide a reproducible install. Development and production both prohibit remote script execution; no web server or secrets are shipped.

The popup separates DOM extraction, current-document orchestration, preferences, downloads and presentation. Scans are ephemeral in the open popup; only preferences persist. Closing the popup discards results and pending preparation. On installation/update, cleanup removes only known Getter result/cache keys and conservatively identified historical URL snapshot keys. Preferences, false options and unknown preference keys survive. The popup retries an idempotent migration on open. Background cleanup never overwrites preferences.

## Access and limits

- `activeTab` and `scripting` cover an explicit toolbar invocation. No standing or optional all-site host grants are requested. Scans do not edit page IDs, borders or other DOM content.
- `webNavigation` is retained only to enumerate frames in the selected tab on request; there is no background navigation listener or browsing log. Up to seven same-origin child frames plus the main document are inspected. Browser-provided document IDs are pinned and rechecked. Cross-origin, opaque, inaccessible and excess frames are explicitly reported as omitted; the product does not claim an exhaustive scan of all frames, pseudo-elements, shadow roots or background images.
- Main extraction stops at 4,000 nodes/100 ms; each child at 1,000 nodes/40 ms. Each result category is capped at 500 after aggregation. A five-second orchestration timeout/cancellation invalidates late results; already injected read-only work is bounded, not remotely killed.
- `storage` persists display preferences only. `downloads` starts an explicit download and observes only owned download IDs while the popup is open. Only prepared local blob URLs are passed to Chrome's downloader, so it cannot follow remote redirects or send site cookies. Started, completed, interrupted and unknown are separate messages. No broad download history query is made.
- Previews are opt-in. File-size reads and ZIP generation happen only on explicit requests, never during rendering. File-size reads, individual downloads and ZIP fetches require HTTPS without embedded credentials, omit credentials/referrer, reject redirects, and respect browser CORS/activeTab access. The content security policy also restricts connections and preview images to HTTPS (plus packaged images). Hosts that reject access are unavailable without requesting more privileges. Individual downloads use the same bounded fetch path as ZIP preparation. This is a deliberate limit, reported in the UI, rather than restored all-site access.
- ZIP: up to 40 files, 8 MiB each, 32 MiB total, one streamed fetch at a time, eight seconds per fetch, sixty seconds preparation. Preserve supported image MIME extensions; no renaming everything to JPEG. Count skipped/oversized/unavailable images and report zero-success failure. Cancellation stops new requests. ZIP assembly is bounded by the byte cap; cancellation during assembly discards the result before saving. Preparation ends before a separate Save ZIP decision: included/unavailable/omitted counts are visible first, with Save ZIP and Discard actions. Prepared blobs stay only in popup memory and are discarded on rescan/navigation/closure. The preparation timer ends before waiting for the person. Create the object URL only when Save is selected. Native Save As may close the popup; the browser Downloads view supplies the final outcome then. Closing releases owned object URLs. A download accepted by Chrome may continue after closing; verify the actual outcome in browser Downloads. Owned URL status observation is capped at two minutes, after which completion is reported as unknown.

## Verification and remaining owner QA

`npm run check` covers extraction without host mutation, caps, preference migration, tab/navigation/document rejection, permissions, exact logo bytes and package inventory. Download tests cover failed/CORS/oversized/cancelled paths and start/completion races. Browser tests load the built extension into a fresh Chromium profile with **test-only localhost host grants** and synthetic pages, exercise real script injection, stored options, frame omission, navigation and actual image/ZIP downloads. HTTPS image responses are fulfilled by synthetic browser routes; this verifies URL/CSP/redirect behavior, not an actual TLS server. Insecure URLs and downgrade redirects must not reach the local HTTP endpoint from the extension. The sizing regression opens the actual action popup with `chrome.action.openPopup()` and measures only `chrome.extension.getViews({ type: "popup" })` from an inactive extension tab. Viewport emulation is disabled, a 1600 × 1200 headless screen supplies desktop space, and the test checks automatic 720 × 600 bounds, more than 350 pixels of results height, a visible footer, no horizontal overflow and all ten preferences fitting. This is an automated headless popup check, not a physical toolbar click or a human-QA verdict. A second actual-popup case on an 800 × 600 screen checks scrolling to the last preference, image download, ZIP and footer actions when Chrome limits the viewport height. The footer may scroll on a constrained screen; fixed footer visibility is asserted only at the tested full desktop popup size. The standalone-tab light/dark checks remain separate. This is not a claim that the shipping activeTab toolbar permission gesture has been qualified. The shipped manifest is separately checked to contain no host grants.

Automated browser testing is a required quality gate for Getter changes affecting the popup or browser-visible behavior. `npm run test:browser` runs in the existing `Getter checks` CI job; required failures block readiness for human QA.
